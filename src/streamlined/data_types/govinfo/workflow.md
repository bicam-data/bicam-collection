# govinfo workflow

Our next step is to apply the same logic from @/abstract and @/base to allow us to populate from the govinfo data source. Similar normalization/cleaning logic should apply, but the scraping logic is different, we don't need specific expected keys, and all of the id_fields will either be named packageId, package_id, granuleId, or granule_id. Each main data type only needs the "collection code" from the config. That then leads into the scraping logic. Here is the workflow:

1) we take the base URL of <https://api.govinfo.gov/collections/>, and then append the collection code from the config.yaml to the end (like <https://api.govinfo.gov/collections/BILLS>) to create the request URL for the list data. The same logic for fromDate, toDate, offset, and limit apply for this link.
2) We make the request. The data will always be found by accessing a list of dicts under the key "packages" in the main response body. In the main response body, "count" gives the total number of main items in that request, and "nextPage" gives the pagination link.
3) We store each entry in the relevant {data_type}_list_raw table. The source_doc_id is the "packageId" field. To get the full data, we attach an API key to the value retrieved from the "packageLink" field in the list entry, and take that data as the "full" data to store in {data_type}_raw with its value for "packageId" as the source_doc_id.
4) Next, we if the config has "has_granules: True" and "granule_name: {granule_name}" fields in the config, we make a request to the value found in the "granulesLink" key that is in the full data (after adding the API key and changing the page size to 1000). If we have a "granule_doc_class" parameter in the config, we also add that to the URL (just by adding &granuleClass={granule_doc_class}). That will take us to *another* set of list data for these granules.
5) This list data is of a similar structure. In the main response text, we have "count" for the total amount of granules, "nextPage" for the pagination data, and "granules" for a list of dictionaries with granule-level list data. We store the granule-level list data in a {granule_name}_list_raw table with "granuleId" as the source_doc_id, and use the value in "granuleLink" (with the API key added on) to access the FULL data for the granule to put in {granule_name}_raw with "granuleId" as the source_doc_id.
6) If the "granules" field in the main response text is empty, or there is no "granulesLink" field in the full data type, skip it as it has no related granules.
7) the normalizer and cleaner logic stays the exact same.
